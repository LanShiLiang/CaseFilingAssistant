# Case Filing Assistant 开发与仓库规范

版本：v0.2

日期：2026-08-06

## 1. 目的

本规范约束 MVP 的代码、依赖、数据、生成物、提交、评审和发布。法律产品的工程质量底线是：任何进入文书的字段可追溯，任何发布物可复现，任何敏感数据不进入 Git、日志、缓存或镜像。

当前仓库已实现可运行 MVP。以下命令均由根目录脚本统一封装；新增流程不得绕开锁文件、契约漂移、测试或制品审计门禁。

## 2. 仓库内容分类

| 分类 | 典型路径 | Git | 构建上下文 | 最终制品 |
|---|---|---:|---:|---:|
| 产品/设计/架构输入 | `outputs/` | 是 | 否 | 否 |
| 应用源码 | `apps/web`、`services/api` | 是 | 按目标最小化 | 仅编译/运行必需文件 |
| 共享源码 | `packages/*` | 是 | 按依赖图 | 仅消费者需要的编译结果 |
| 基础设施定义 | `infra/`、未来 `compose.yaml` | 是 | 仅构建所需 | 不复制进应用 runner |
| 测试代码与虚构 fixtures | `tests/`、`test/` | 是 | builder 可用 | 否 |
| 上传、OCR、数据库和导出 | `data/`、`uploads/`、`ocr-cache/`、`exports/` | 否 | 否 | 否，仅运行 volume |
| 缓存、覆盖率、报告 | `.turbo/`、`.next/cache/`、`.pytest_cache/`、`coverage/` | 否 | 否 | 否 |
| secret 与本地配置 | `.env*`（除示例）、密钥 | 否 | 否 | 否 |

`outputs/` 可以提交供团队审核，但它永远只是研发输入。生产代码不能在运行时读取设计 HTML、方案 Markdown 或 Canva/PPTX 资源。

## 3. 数据与隐私

禁止提交或传播：

- 真实判决书、调解书、身份证照片、签名、印章和案件附件。
- 真实姓名、证件号、地址、电话、银行账户、财产线索和 OCR 全文。
- 上传件、解析缓存、数据库文件、生成 DOCX/PDF/PNG、导出包和诊断包。
- access token、私钥、证书、cookie、`.env` 和第三方服务凭据。

测试要求：

- 所有 fixtures 完全虚构，使用显著测试姓名、不可对应真实个人的号码和专用测试图片。
- 不把真实材料“脱敏后”直接当 fixture；脱敏遗漏不可可靠证明。
- 日志断言检查请求/响应正文、文件名原文和敏感字段不会输出。
- 截图、失败视频、trace 和渲染结果按敏感数据处理，默认不提交 Git，也不进入公开 CI artifact。

发现疑似真实信息时立即停止提交和传播，隔离文件、完成复核，并在必要时轮换泄露凭据。不得只靠新增 `.gitignore` 处理已经进入历史的 secret。

## 4. 分支与提交

- 每个提交只覆盖一个可解释的变更范围，不混入无关格式化或生成物。
- 提交前先检查 `git status --short`、`git diff --check` 和 staged diff。
- 不覆盖他人未提交改动，不使用破坏性 reset 清理工作区。
- 生成代码与来源契约在同一提交；OpenAPI/client drift 检查必须通过。
- 迁移只前向新增，已进入共享分支的迁移不得重写编号或历史内容。
- 重要架构变化在方案/架构文档中记录理由、风险、替代方案和验证方式。
- commit message 使用清晰的范围，例如 `docs: align MVP architecture`、`feat(web): add eligibility gate`、`fix(worker): reject stale lease publish`。

评审至少关注：产品范围、来源/确认链、revision 失效、幂等和租约、敏感信息、契约兼容、制品内容、文书渲染。

## 5. 依赖与锁文件

### 5.1 JavaScript/TypeScript

- 根目录只使用 pnpm；提交唯一 `pnpm-lock.yaml`，禁止混入 npm/yarn/bun lockfile。
- workspace 内部依赖使用 `workspace:` 协议，禁止发布前隐式解析到 registry 同名包。
- 生产依赖和开发依赖分开；运行镜像只安装/复制生产所需内容。
- 依赖升级单独提交，包含 lockfile 差异、构建大小变化、许可证与漏洞检查结果。
- Turborepo cache inputs 不包含 `.env`、案件数据或 `outputs/`。

### 5.2 Python

- `services/api/pyproject.toml` 是声明来源，`uv.lock` 是精确解析结果；开发、CI 和镜像使用 frozen lock。
- 禁止同时维护会漂移的手写 `requirements.txt`；第三方工具若需要导出文件，应由 lock 自动生成且不作为第二来源。
- API、worker、migrate 使用同一 lock 与 Python 版本。
- OCR/LibreOffice/Poppler/字体等系统依赖固定版本或镜像 digest，并记录许可证与运行能力检查。

### 5.3 通用规则

- 不使用浮动 `latest` 作为可发布基础镜像或数据库版本。
- 不在 install/build 脚本中静默联网下载 OCR 模型；模型应在构建或显式初始化阶段固定并校验 hash。
- 新依赖必须说明为何不能用标准库或现有依赖解决，以及对包体、启动时间、漏洞面和许可证的影响。

## 6. 代码边界与所有权

- `apps/web` 拥有 Web 页面、交互和响应式实现，不拥有服务端法律规则。
- `packages/ui` 只包含 Web/DOM 通用组件；不得引用案件 contracts 形成领域 UI 大包。
- `packages/design-tokens` 只包含跨端纯数据和转换脚本。
- `packages/contracts` 由前后端共同维护，只放 OpenAPI 快照、生成类型、稳定错误码和协议工具。
- `services/api` 是唯一 Python project，API、worker、迁移通过不同 entrypoint 复用 application/domain 层。
- `infra` 拥有容器、健康检查、启动编排与制品审计，不持有业务规则。
- `apps/miniprogram` 在 MVP 中不参与任何默认任务；未来客户端不能复制服务端生成门禁或直接复用 DOM UI。

禁止循环依赖。共享包只能向更底层的 contracts/tokens 引用；应用可以依赖共享包，共享包不能反向依赖应用。

## 7. 生成代码、迁移与模板

- OpenAPI client、类型和枚举是生成物，文件头标记来源和生成命令，禁止手改。
- CI 重新生成并要求 `git diff --exit-code`，防止协议漂移。
- 数据库迁移包含 upgrade 路径和必要约束；涉及数据修复时使用小批量、可观察、可重入策略。
- 文书模板、规则 metadata 和字体 manifest 都有稳定 ID、版本、hash 和生效说明。
- golden 文书只使用虚构数据；模板更新必须附渲染前后差异和人工视觉核验。
- 编译产物、测试报告、预览图和本地导出不提交；只有经明确评审的设计审核资源可在 `outputs/design` 保存。

## 8. 配置与环境变量

- 配置使用类型化 schema，API、worker、migrate 共用定义；缺少必需配置应启动失败并给出非敏感错误。
- 提交 `.env.example` 时只放安全占位和说明，绝不放可用 secret。
- 前端只有明确标记为公开的变量可以进入浏览器 bundle；内部 API 地址、数据库 DSN 和路径不得使用公开前缀。
- local/dev/test/production-like profile 的差异显式记录；不能靠未提交个人文件改变法律规则或模板版本。
- 路径在配置边界解析，API 和日志只传 opaque ID/key，不返回本机绝对路径。

## 9. 验证命令

根任务封装常用验证，避免每个开发者拼装不同命令：

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm contracts:check
pnpm build
pnpm artifact:audit
pnpm verify
pnpm test:e2e
docker compose up --build
```

Python 底层命令由 Turbo/root script 调用，不要求使用者维护第二套参数。`pnpm test` 包含 Web 单元测试和后端单元/集成测试；`pnpm verify` 再聚合 lint、typecheck、契约漂移、生产构建和制品审计；`pnpm test:e2e` 使用隔离数据库和运行时生成的虚构 fixture 验收桌面/移动完整闭环。CI 与本机使用相同脚本入口和 frozen lock。

提交前仍须执行 `git diff --check`，并人工检查 Markdown 链接/代码围栏、绝对路径、疑似敏感信息和未提交设计生成目录。

## 10. 变更对应的最小验证

| 变更 | 最小验证 |
|---|---|
| UI/响应式/动效 | lint、typecheck、component、a11y、多 viewport Playwright、reduced-motion |
| OpenAPI/contracts | schema validation、codegen no-diff、前后端契约测试 |
| validation/revision | unit、事务集成、旧 revision 拒绝发布测试 |
| job/worker | 并发领取、lease 过期、重试、幂等、优雅退出集成测试 |
| storage/privacy | 路径逃逸、hash、原子发布、清理、日志脱敏和内容扫描 |
| 迁移 | 空库、上一版本升级、失败阻断启动 |
| 文书模板/规则 | deterministic golden、DOCX/PDF/PNG 实际渲染和人工视觉核验 |
| Docker/依赖 | clean build、health chain、SBOM、漏洞/许可证、artifact audit、大小差异 |
| README 启动说明 | 干净环境完整复现、停止/重启/保留数据 |

## 11. 制品规范

发布物采用 allowlist，而不是复制仓库后删除：

- Web：standalone Node server、静态资源、允许的 public 文件和许可证。
- 后端：冻结运行依赖、应用 package、迁移、规则/模板/字体 manifest 和必要系统库。
- 数据：只存在用户本地 volume，不是镜像层或发布压缩包内容。

以下内容出现即失败：

```text
.git/
outputs/
design/
work/
tests/
test-results/
playwright-report/
coverage/
*.pptx
需求/方案 Markdown
.env*
上传件、OCR 缓存、数据库、导出件
本机绝对路径
```

许可证文件必须使用单独 allowlist，不能为了保留许可证而放开所有 Markdown。

## 12. 完成定义

一个功能只有同时满足以下条件才算完成：

1. 产品范围和设计状态明确，没有绕过人工确认或草稿边界。
2. 契约、实现和生成客户端一致。
3. 正常、失败、重试、刷新/重启和 revision 变化均有验证。
4. 日志、缓存、截图、制品和 Git 不含敏感内容。
5. 对应测试、渲染或视觉检查通过。
6. 相关文档更新，未完成限制明确写出。

“在开发机能运行”不等于发布完成；“命令已写入 README”也不等于一键启动已实现。
