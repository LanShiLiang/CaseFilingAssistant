# Case Filing Assistant v0.1.0 资深架构专家复核与优化建议

版本：v1.0

复核日期：2026-08-07

复核对象：commit `89b46505ff18a4468e82b92d618d2d6f0aa36ce2`、当前前后端代码及《架构 Review 报告 v0.1.0》

范围：只评审可靠 MVP 的代码架构、并发一致性、契约边界与发布可信度；不改变业务流程，不增加账号、平台、微信小程序、生成式 AI 或法院外部操作。

## 1. 独立结论

主审报告对整体方向的判断成立：技术选型没有必要推倒重来，真正的问题是既定方案中的模块边界、不可变输入、租约语义和生成契约没有完整落到代码。项目应继续保持 Next.js 单 Web、FastAPI 模块化单体、同一 Python package 的 API/worker/migrate，以及 PostgreSQL 任务表，不应拆微服务或增加 Redis/Celery。

但主审报告的优先级有两处需要修正：

1. 当前最高优先级遗漏是**解析任务的陈旧状态回写竞态**。`jobs.py:75-108` 在执行耗时解析前读取 `Matter`，解析完成后只比较这个 Session 内可能已经陈旧的 `matter.revision`，没有重新加锁或刷新。用户若在解析期间保存确认字段，worker 可能把旧的 `facts/sources/confirmations` JSON 覆盖回数据库。这比单纯缺少快照更接近当前可发生的数据正确性问题。
2. OpenAPI 双轨确实存在，但“立刻生成全部 RTK Query endpoints”不应列为 P0。现有服务端响应 schema 本身大量使用 `str` 和 `dict[str, Any]`；如果不先强化 schema，自动生成只会把模糊契约自动化。应先建立强类型协议，再让真实消费者使用生成类型，完整 endpoint codegen 可作为随后的一步。

综合风险排序建议为：

| 级别 | 必须解决的问题 | 风险性质 |
|---|---|---|
| P0 | 解析结果基于陈旧 `Matter` 回写，可能覆盖用户确认数据 | 当前数据正确性与审计链风险 |
| P0 | job 完成、失败、续租未用 lease token 做 CAS，长任务无续租 | 过期 worker 仍可发布或覆盖新 worker 结果 |
| P0 | 缺少真实 PostgreSQL 并发测试，SQLite E2E 无法证明 `SKIP LOCKED`/lease 语义 | 可靠性承诺没有可重复证据 |
| P1 | 生成读取 ORM `Matter`，没有持久化、版本化的纯数据生成输入 | 生成内容与校验上下文难以证明一致 |
| P1 | 前端工作台、后端 route/service 与生成器职责过重 | 可读性、变更隔离与定向测试成本高 |
| P1 | OpenAPI schema 偏弱且 UI 使用手写类型/endpoints | 协议漂移可绕过当前检查 |
| P1 | Compose 阻止 worker 故障时启动 Web，与“可降级查看”目标相反 | 故障隔离与可恢复体验不一致 |
| P2 | 初始迁移、最终镜像审计、readiness、存储发布/清理语义不足 | 发布和长期演进可信度不足 |

## 2. 对主审报告的逐项复核

### 2.1 完全同意的结论

1. **`MatterWorkbench` 是 God Component。** 该文件 408 行，主组件同时持有 Matter/Job/Generation 查询、7 个本地状态、上传/保存/校验/生成/确认命令、轮询和四步 JSX。commit 的两条行内评论准确指向了职责与目录语义问题，增加注释不能替代拆分。
2. **`HomePage.handleCreate` 的业务语义不透明。** 事件函数内硬编码 eligibility version、幂等键、协议调用、跳转和错误展示。应提炼命名清楚的应用 hook，但不需要为一个用例引入命令总线。
3. **前端复制了服务端权威门禁。** `domain.ts:54-64` 自行推导步骤可达性；服务端响应又不提供结构化 step gates。两边长期必然漂移。金额的 JS `Number` 只能作为未保存预估，不能成为生成资格或法律金额权威值。
4. **后端 route 与应用用例混层。** `api.py:195-267` 直接完成锁定、revision 校验、规则调用、ORM 写入、job 创建和 commit，HTTP 层已经承担事务用例。
5. **裸 JSON 缺少类型和版本边界。** `models.py:29-31` 的 `facts/confirmations/sources` 可继续保留为 MVP 的 JSON 列，但任何读写都应经过版本化值对象，不能继续在多处手工复制和修改 dict。
6. **worker lease 没有闭环。** `claim()` 生成 token 却只返回 job ID；`process()`、成功、失败均不匹配 token，也没有工作租约 heartbeat。主审报告对此判断准确。
7. **renderer 不应依赖 ORM。** `generation.py` 的四类文书与 ZIP 组装都读取 `Matter`。生成输入应是可序列化、经过校验的纯数据结构。
8. **CI 与制品审计不足。** 仓库没有 `.github/workflows`；`artifact-audit.ps1` 只检查源码目录中的少量扩展名和 `.dockerignore` 字符串，不能证明最终 image/filesystem 内容。
9. **已发布 0001 不应改写。** 后续迁移必须使用显式 `op.*` 并验证从空库和 v0.1.0 库升级；不以 downgrade 代替备份恢复。

### 2.2 部分同意、需要调整的结论

#### 不可变快照：同意目标，调整实现与优先级

主审把独立 `ConfirmationSnapshot` 列为第一 P0，目标正确，但不能让“新增一张完整快照体系”遮住当前解析回写竞态。当前生成 worker 在生成前重新校验，并在写入 Blob 后 `session.refresh(matter)` 检查 revision；它虽然无法提供强审计证明，也会产生孤儿文件，但已能挡住一类旧 revision 发布。

可靠 MVP 的最小落地可以分两步：

1. 先定义 `GenerationInputV1`，在 `start_generation` 的短事务中从已确认字段构造、校验、序列化并保存到 Generation；worker 只读取该输入，不再读取 `Matter`。
2. 当校验记录需要审计复用时，再引入 `ValidationRun`/`ConfirmationSnapshot`，让 Generation 引用同一 validation snapshot。不要同时建立多套语义相近的 DossierRevision、Snapshot、Context 表。

#### OpenAPI：同意消除双轨，反对先 codegen 后建模

`packages/contracts/src/index.ts` 的手写 `SourceReference.extraction_method` 只允许 `text | ocr | user`，而服务端在 `services.py:363` 实际写入 `deterministic`；这已经是可验证的协议漂移。与此同时，`schemas.py` 把多个状态声明为普通 `str`，来源声明为 `dict[str, Any]`，导致生成的 OpenAPI 也无法表达完整 enum 与嵌套结构。

推荐顺序：

1. 服务端用 Pydantic `Literal`/显式 response model 固化状态、错误码、来源和 gate。
2. 从 `operations`/`components` 生成并直接派生 UI 使用的 request/response 类型，删除手写协议 shape。
3. 先保留一个很薄的 RTK Query adapter 也可以，只要 endpoint 的入参与返回值直接引用生成类型。
4. 当 endpoint 数量或多个客户端确实需要时，再引入 `@rtk-query/codegen-openapi` 生成 hooks；不把 codegen 本身当作正确性证明。

#### 前端步骤路由：不作为强制架构要求

刷新后回到步骤 1 是体验和恢复性缺陷，但不必为 MVP 强制建立四个页面路由。单路由配合服务端 gate 推导“建议恢复步骤”，并以校验后的 search param 表示当前步骤，已经足够。核心约束是不可到达状态不能只由本地 `useState` 决定。

#### `BlobStore` Protocol：保留小端口，不提前抽象多后端

隔离 `stage/publish/open/delete` 语义有价值，尤其便于注入提交失败、失租和清理失败；但不应出现通用对象存储 SDK、S3 配置或复杂仓储层。MVP 只保留一个 Local 适配器。

### 2.3 不同意或不建议照搬的部分

1. **不以 `MatterWorkbench.tsx` 40 行以内作为验收标准。** 行数不是架构边界。验收应看页面是否只组合 controller 与 step view、业务动作是否可独立测试、每个模块是否只有一个变更原因。
2. **不一次性套用全局 CQRS、通用 Repository 基类、通用 UoW 或依赖注入容器。** 当前只有一个窄业务流程，显式 use-case function + 明确事务即可。通用框架会增加间接层而没有第二个消费者证明价值。
3. **不要求立刻建立完整四层目录迁移。** 先按垂直业务切片迁移最危险的 `documents/jobs/generation`，再处理 matters/validation；避免一次性移动全部文件造成大 diff 和回归盲区。
4. **不把 Storybook 作为步骤组件可测的前提。** Testing Library 的窄 props 组件测试即可；只有设计团队确有独立组件审阅流程时再引入 Storybook。

## 3. 主审报告遗漏的关键风险

### 3.1 P0：解析任务可能覆盖用户已确认字段

实际时序如下：

```text
worker 读取 Matter(revision=N, confirmations=旧值)
  → 执行耗时 PDF/OCR 解析
用户保存确认字段并提交 Matter(revision=N+1, confirmations=confirmed)
  → worker 仍在旧 Session 中看到 revision=N
  → `matter.revision == job.input_revision` 判断通过
  → worker 用旧 dict 构造并提交 facts/sources/confirmations
```

`save_confirmed_facts()` 使用行锁本身不能保护一个已经在另一个长事务中加载的 ORM 对象。整改要求：

- claim 后先读取不可变任务输入，耗时解析在无业务事务状态下完成。
- 发布解析结果时开启新的短事务，按 `matter_id + input_revision` 加锁并重新读取当前 confirmations。
- 只有 revision 仍匹配且字段当前不是 confirmed 才合并候选；使用当前数据库 JSON 作为 merge base。
- 更新 job/document 时同时匹配 lease token；失租或 revision 不匹配只记录 superseded，不发布候选。
- PostgreSQL 集成测试必须用事件/屏障稳定复现“解析中用户保存”的交错，不依赖 sleep 碰运气。

### 3.2 P0：当前测试不能证明声明的队列可靠性

`test_api_flow.py` 使用单进程 harness 顺序执行 `run_next_job()`，能证明业务闭环，不能证明：

- 两个 worker 不会领取同一 job。
- lease 过期后旧 worker 无法完成发布。
- heartbeat 能覆盖超出租约时长的 OCR/渲染。
- DB 短暂中断后 retry/terminal 状态收敛。
- SQLite 与 PostgreSQL 的锁语义差异不会掩盖问题。

因此，在并发实现之前先增加真实 PostgreSQL integration suite；否则对任务代码的重构没有可靠回归网。

### 3.3 P1：能力降级目标与 Compose 依赖冲突

架构规范要求 worker 故障时 Web 仍能打开并显示降级原因，但 `compose.yaml:83-87` 让 Web 同时依赖 API 和 worker healthy，worker 初始不健康时 Web 根本不会启动；`CapabilityResponse` 也没有 worker 在线/队列可处理状态。

建议：Web 启动只依赖 API ready；API capability 汇总脱敏的 worker heartbeat、运行依赖和稳定降级码；上传/生成由服务端 capability 阻断，事项查看继续可用。不要把 worker 健康混入 API liveness/readiness。

### 3.4 P1：文件与数据库提交缺少统一发布语义

上传在 `services.py:280` 先写 Blob，随后才提交 Document/Job；生成在 `jobs.py:133-134` 先写正式 Blob，再提交 Generation。数据库冲突、失租或进程退出会留下孤儿文件。

MVP 不需要通用 outbox，但需要小而明确的规则：

- Blob 先写 staging key。
- 数据库 CAS 成功后发布为正式 key，或数据库记录 staging key 并由清理器按状态收敛。
- 定时清理只删除超过安全窗口、且无活动 DB 引用的 staging/orphan key。
- 删除与清理日志只记录 blob ID/hash 前缀和错误码，不记录原始文件名或正文。

### 3.5 P1：幂等键并发冲突未收敛为协议结果

`create_matter()` 采用“先查 IdempotencyRecord、再创建 Matter 和唯一记录”。两个同 key 并发请求可能让后一个在唯一约束处抛出数据库异常，而不是返回第一次的相同响应。建议捕获唯一冲突后回滚并重读记录，验证 request hash 后返回稳定结果；增加并发测试。

### 3.6 P1：校验结果没有持久化审计实体

当前只有 `Matter.validated_revision`，validation issues 只返回给调用方，没有规则版本、输入 hash、issue 清单和运行记录。即使 generation manifest 记录 rule/template version，也无法回答“当时哪次校验允许生成”。

最小方案是保存 `ValidationRun`：`matter_id/revision/input_hash/rule_version/issues/passed/created_at`。Generation 可先引用 `validation_run_id` 和 `GenerationInputV1`；不要把 OCR 全文复制进快照。

## 4. 推荐目标架构

### 4.1 总体形态

继续使用模块化单体和单部署仓库：

```text
Browser
  → Next.js 同源代理
  → FastAPI HTTP adapter
  → 显式 use case（单事务边界）
  → typed domain state / repository adapter
  → PostgreSQL + LocalBlobStore

Worker entrypoint
  → JobQueue claim/heartbeat/CAS
  → ParseHandler | GenerateHandler
  → 同一 typed domain state / repository adapter
```

HTTP 与 worker 是两个入口，不是两套领域实现。未来小程序仍调用同一 API，不构成新的后端入口或复制法律规则的理由。

### 4.2 前端最小结构

```text
apps/web/src/
  app/                              # 路由、layout、同源 proxy
  features/
    eligibility/
      EligibilityGate.tsx
      useCreateEligibleMatter.ts
    matter-workbench/
      MatterWorkbench.tsx           # 组合 controller 和 view
      useMatterWorkbench.ts         # server state、command、polling
      workflowPresenter.ts          # 服务端 gate → 展示态
      steps/
        PartiesAndBasisStep.tsx
        ApplicationStep.tsx
        ReviewStep.tsx
        ExportStep.tsx
      components/
        UploadControl.tsx
        ConfirmableField.tsx
  store/api/
    caseApi.ts                      # 生成类型驱动的薄 adapter
    pollingPolicy.ts
```

边界要求：

- step 组件通过窄 props 接收 view model 和 command，不直接读取整个 Redux store。
- controller 管理轮询、revision 失效、未提交表单、命令状态和错误恢复，不包含法律门禁或金额权威计算。
- 服务端返回 `step_gates`、稳定 error code 和 decimal 字符串；前端 presenter 只负责图标、文案和 disabled 状态。
- `packages/ui` 只接收真正无案件语义且有两个以上消费者的 DOM 组件；不要为了“复用”把 ConfirmableField 的案件语义搬进去。

### 4.3 后端最小结构

按风险最高的垂直切片逐步形成：

```text
services/api/app/
  http/                             # FastAPI routes、request/response 映射
  matters/                          # create/get/save use cases + typed dossier
  documents/                        # upload、parse publish、来源合并
  validation/                       # rules、ValidationRun、step gates
  generation/                       # GenerationInputV1、renderers、package
  jobs/                             # queue repository、lease、handlers、retry classifier
  infrastructure/
    sqlalchemy.py
    local_blob_store.py
  entrypoints/                      # api/worker/migrate
```

每个修改型 use case 明确完成：加载/锁定 → 检查 revision/状态 → 调用纯规则 → 写入业务记录/job → commit。不要建立通用 CRUD repository；只为并发、存储和测试需要定义窄端口。

### 4.4 三类必须类型化的数据

1. `DossierV1`：事实、确认状态、来源引用和 schema version；仍可存 JSON。
2. `ValidationRunV1`：输入 hash、rule version、issues、passed、matter revision。
3. `GenerationInputV1`：只含已确认字段、确定性计算、来源摘要、snapshot hash、validation_run_id、template/rule/schema version；renderer 唯一输入。

禁止把 SQLAlchemy `Matter`、UploadFile、本机 Path、OCR 全文放入 renderer 或公开契约。

## 5. 分阶段变更建议

### 阶段 0：先建立并发回归网

- 新增 PostgreSQL 集成测试入口，保留现有 SQLite 快速测试。
- 用 barrier/fake slow parser 覆盖解析中保存、双 worker claim、失租后旧 worker 完成、生成中 revision 变化。
- CI 先运行 lint/typecheck/unit/contract，再运行 PostgreSQL concurrency suite。

退出标准：上述交错场景在旧实现上能稳定暴露失败，成为后续修复的保护网。

### 阶段 1：修正 P0 并发与发布语义

- `claim()` 返回 `ClaimedJob(job_id, lease_token, input_revision)`。
- heartbeat、completed、failed、retry 全部以 `id + lease_token + running` 做 CAS，并检查 affected row。
- 解析计算与发布分离；发布时重新锁 Matter、读取当前 JSON、校验 revision 后 merge。
- 生成与上传使用 staging/publish/cleanup；SQLite 明确限制为单 worker 开发模式。

退出标准：失租 worker 和旧 revision worker均无法修改当前 Matter、Generation、Document 终态或正式 Blob 引用；并发集成测试全部通过。

### 阶段 2：固化生成输入与服务端权威状态

- 引入 `DossierV1`、`ValidationRunV1`、`GenerationInputV1`。
- generation renderer 改为纯数据输入，拆分 DOCX/PDF/来源表/ZIP assembler。
- API 返回 step gates、amount computation 与稳定错误码；前端删除权威规则复制。
- `services.py`/`api.py` 的修改型逻辑迁入显式 use cases。

退出标准：renderer 无 ORM import；每个 Generation 可追溯到 validation run、input hash 和版本；修改任一确认事实后旧 validation/generation 不可下载。

### 阶段 3：前端可读性与契约单轨

- 拆工作台 controller、四个 step view、轮询 policy 和上传组件。
- 强化 Pydantic OpenAPI schema，再删除 contracts 手写响应类型。
- endpoint adapter 直接引用生成 operations/components；根据维护收益决定是否生成全部 RTK Query hooks。
- HomePage 使用命名清楚的创建用例 hook。

退出标准：commit 评论所指逻辑可通过目录和命名理解；步骤组件和 controller 可独立测试；手写 `SourceReference`/`Matter`/`Generation` 协议 shape 数量为 0。

### 阶段 4：发布可信度

- 增加 GitHub Actions、空库/上一版本迁移、真实容器 smoke。
- Web 只依赖 API ready；补 worker capability 降级链路。
- 区分 source-boundary audit 与最终 image artifact audit，输出最终文件/层/大小清单。
- 从 0002 起只用显式 Alembic 操作，不改写已发布 0001。

退出标准：tag 发布前可重复证明 PostgreSQL 并发、Compose 启动/降级、迁移、E2E 和最终镜像 allowlist 均通过。

## 6. 架构验收标准

### 正确性

- [ ] 解析期间用户保存的 confirmed 字段永远不会被旧 worker 改回 pending 或旧值。
- [ ] 任何 job 的续租、完成、失败、重试都必须持有当前 lease token。
- [ ] 失租 worker 可以继续浪费计算，但不能发布 DB 状态或正式 Blob。
- [ ] renderer 只消费持久化、版本化、可 hash 的 `GenerationInputV1`。
- [ ] validation、generation、manifest 可通过 ID/hash/version 建立审计链。

### 前端边界

- [ ] MatterWorkbench 只组合 controller 与 step views，不内嵌所有 mutation 实现和四步字段细节。
- [ ] UI 不实现权威 step gate 或 decimal 金额规则。
- [ ] 轮询在终态、卸载、页面隐藏和事项切换时有明确停止/恢复策略。
- [ ] 刷新后由服务端状态恢复可达步骤，不依赖未持久化的 `useState`。

### 契约与后端边界

- [ ] OpenAPI 对 status、kind、source method、gate 和 error code 提供强类型 schema。
- [ ] TypeScript 不再维护与 OpenAPI 平行的请求/响应 interface。
- [ ] HTTP route 不直接完成跨多实体的事务编排；worker handler 与 API 可复用同一领域规则。
- [ ] JSON dossier 读写统一经过 schema version 和 Pydantic 校验。

### 发布与恢复

- [ ] PostgreSQL 集成测试覆盖双 worker、lease expiry、revision race 和幂等并发。
- [ ] worker 不健康时 Web 仍能查看事项并显示脱敏的 capability 降级原因。
- [ ] 最终镜像文件清单不含 `outputs/`、tests、设计/需求文档、本地案件数据、secret 或本机绝对路径。
- [ ] v0.1.0 数据库可前向升级；迁移失败不会启动 API/worker。

## 7. 应避免的过度设计

- 不拆微服务，不创建第二个 worker Python 项目。
- 不引入 Redis、Celery、Kafka、Temporal、Kubernetes 或通用消息总线。
- 不为了未来对象存储实现 S3；只定义当前故障测试需要的窄 BlobStore 端口。
- 不建立通用 BaseRepository、通用 CQRS 框架或 service locator。
- 不把所有 JSON 立即拆成关系表；先用版本化 Pydantic schema 约束现有列。
- 不用单文件行数、目录层数或“所有组件都进 packages/ui”作为架构 KPI。
- 不因未来微信小程序复制前端业务规则；稳定 OpenAPI、服务端 gate、错误码和纯数据 token 即可。
- 不在本轮增加 AI/OCR 云服务、账号、权限、后台管理或自动法院操作。

## 8. 最终建议

v0.1.1 应把“解析回写竞态 + lease token CAS + PostgreSQL 并发测试”列为 release blocker；将不可变生成输入、服务端 step gates、强类型 OpenAPI 和工作台拆分列为紧随其后的架构整改。CI、镜像审计和降级启动链路应在下一次公开 release 前完成。

主审报告无需推翻，但建议主报告汇总时调整三点：补入解析回写竞态并升为 P0；将 OpenAPI endpoint codegen 降为 P1 且先强化 schema；取消 40 行、强制四步路由等实现型指标，改用职责、正确性和可测试性验收。
