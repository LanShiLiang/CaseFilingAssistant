# 全国版强制执行材料生成助手：前端技术方案

版本：v0.5

日期：2026-08-06

决策状态：与 v0.5 交互设计稿对齐的本地 MVP 实现基线

目标：以桌面 Web 为基准，同时保证移动 Web 核心四步流程可用；通过清晰的状态、契约和构建边界，实现“本人办理、一名自然人申请执行人、一名自然人被执行人、一项明确金钱给付义务”的可靠本地闭环。当前版本不实现登录、律师模式、多角色编辑、微信小程序或生成式 AI。

## 0. 本次优化结论

本方案保留 React、Next.js App Router、React-Redux、Redux Toolkit、RTK Query、Ant Design、React Hook Form 和 Zod 技术基线，但按设计稿和 MVP 可靠性要求作以下收敛：

- 工作台统一为四步：当事人与依据、申请内容、检查与预览、导出；上传能力并入步骤 1。
- 首页使用 1—4 编号适用条件和一个总确认复选框。未确认时禁止新建事项。
- 新事项 Header 显示“待上传执行依据”；处理时显示“正在识别执行依据”；只有案号完成用户确认后，后端才返回案号作为事项标题。
- 步骤 1 从执行依据开始。申请执行人身份证正反面都是进入步骤 2 的门禁材料；被执行人身份证正反面是“如有上传”，姓名可从执行依据提取，缺失信息允许手工填写。
- 证件住址不得自动成为送达地址，作出法院不得自动成为申请法院。可以提供显式“带入”操作，但目标字段仍须单独确认。
- 步骤 2 的主要义务、文书金额、履行期限和请求事项候选只来自执行依据，或由用户查看执行依据后手工填写；履行材料只作为已履行金额来源。候选不得自动进入最终文书。
- 将来源、置信度、确认状态、数据版本和产品范围阻断定义为跨端契约，不在组件内依赖中文文案判断业务逻辑。
- 桌面 Web 是视觉基准；移动 Web 是同一 Next.js 应用的响应式形态，必须完成核心闭环，不另建第二套业务状态。
- 新增纯数据 `packages/design-tokens`。未来微信小程序复用 contracts、tokens 和纯领域逻辑，不直接复用 DOM、Ant Design 或 React Web 组件。
- 生产构建使用 Next.js standalone 和多阶段镜像，设计稿、需求文档、测试材料、本地数据、源码缓存不得进入 Web 运行产物。

扩展性通过可替换适配器、稳定契约和无框架共享包实现，不通过提前开发第二版页面或空模块实现。

## 1. MVP 目标、非目标与体验基线

### 1.1 目标

- 支持用户从本地材料完成一项简单强制执行申请草稿的录入、来源核对、检查、预览和导出。
- 每个进入文书的关键字段展示材料来源或“用户填写”，并显示确认状态。
- OCR、规则抽取或预览失败时给出可恢复路径；支持范围内的简单案件可通过手工填写继续。
- 多当事人、代理关系、多项独立义务等情况展示“当前版本不适用”，且没有“忽略并继续”。
- 刷新、重启、短暂断连和 worker 失败后能从服务端恢复，不依赖浏览器保存案件数据。

### 1.2 非目标

- 不实现登录、注册、组织、权限、管理后台、律师工作台和身份模式切换。
- 不实现多个申请执行人、多个被执行人、代理人、组织主体或通用角色编辑器。
- 不实现微信小程序页面，只保留可复用的 contracts、tokens 和纯逻辑边界。
- 不实现生成式 AI、模型设置、外部遥测、法院登录、提交、缴费、送达或联系法院。

### 1.3 设计验收基线

- 以 `outputs/design/case-filing-assistant-design.html` 为页面结构、状态语言和交互动效基准。
- 桌面重点验收宽度为 1280px 和 1440px；移动 Web 最小支持 360px 宽度，重点验收 390px、430px 和 768px。
- 页面可以因设备宽度改变布局，但适用门禁、来源查看、人工确认、阻断和版本失效语义不得改变。
- 设计稿为展示完整视觉状态而预填的“已确认”字段不代表自动确认逻辑。上传或解析完成后必须先进入 `extracted_pending_confirmation`；设计稿中证件识别后直接出现“送达地址”的示例也不得照搬。
- 设计稿是实现输入，不是运行时依赖；HTML、PPTX、预览图不得被 Web 代码引用或复制进生产镜像。

| 层 | MVP 选型 | 明确职责 |
|---|---|---|
| Monorepo | pnpm workspace + Turborepo | 依赖安装、任务编排、缓存和共享包边界 |

| Web 框架 | Next.js App Router | 路由、布局、构建、自托管和同源 API 转发 |
| React 状态绑定 | React-Redux | 通过 Provider 和类型化 hooks 将 store 接入组件 |
| UI 全局状态 | Redux Toolkit | 只管理跨组件、跨步骤的非案件正文 UI 状态 |
| 服务端状态 | RTK Query | API 查询、mutation、内存缓存、轮询和失效 |
| API 生成 | `@rtk-query/codegen-openapi` | 从 FastAPI OpenAPI 生成 endpoints、hooks 与类型 |
| 表单 | React Hook Form + Zod | 未提交草稿、交互校验、字段聚焦和提交转换 |

| 视觉 token | `packages/design-tokens` | 跨端颜色语义、间距、圆角、字号和动效时长的纯数据源 |

| 文档预览 | 服务端分页 PNG + 文本摘要 | 与服务端渲染核验一致，避免浏览器重复解析 PDF |
| 图标 | lucide-react，按图标导入 | 统一工具图标，避免整包进入产物 |
| 单元/组件测试 | Vitest + Testing Library + MSW | 状态、表单、组件和 API 错误恢复 |
| 端到端/视觉测试 | Playwright | 四步闭环、阻断、响应式、动效和版本失效 |

### 2.1 React、Next.js、React-Redux、Redux Toolkit 与 RTK Query

```text
React + React DOM       组件、hooks、事件、渲染和 hydration
        ↓
Next.js App Router      路由、布局、Server/Client 边界、构建和 Node 自托管
        ↓
React-Redux             Provider 与类型化 hooks，不拥有业务状态
        ↓
Redux Toolkit           少量跨页面 UI 状态
RTK Query               服务端资源、请求生命周期、缓存、轮询和失效
```

状态归属只有以下四类：

- 按钮展开、局部提示和弹窗内部状态：React hooks。
- 未提交的表单值、字段错误和 dirty 状态：React Hook Form；Ant Design Form 不再建立第二套表单状态。
- 来源查看器位置以及用户主动调整的导航/分栏状态：Redux Toolkit；当前步骤由路由和服务端门禁派生。
- 运行能力与连接摘要：RTK Query 的 capabilities 查询，不复制到普通 slice。
- 事项、材料、候选、确认卷宗、校验、任务和生成记录：RTK Query；不得复制到普通 slice。

路由参数和可分享的筛选条件使用 Next.js params/search params。案件正文、OCR 全文、身份证号、账户和地址不得进入 URL、普通 Redux slice、`localStorage`、`sessionStorage`、Redux DevTools action payload 或浏览器日志。

Next.js 只承担 Web 层职责。FastAPI 是法律业务、版本、校验和生成规则的唯一服务端；Route Handler 只允许实现健康检查或透明同源转发，不复制领域规则。

### 2.2 Server Component 与 Client Component

- 根 layout 可作为 Server Component，负责静态 metadata、字体回退、样式和无敏感内容的外壳。
- 最近事项、事项标题、工作台和来源查看器都由 Client Component 通过 RTK Query 获取，避免案件数据进入静态产物、构建日志或 Next.js 数据缓存。
- Redux store 通过 `makeStore` 在客户端 Provider 内按工作台实例创建，不导出服务端全局单例。
- `AntdRegistry` 放在根 layout；使用 Ant Design context、交互或浏览器 API 的组件明确标记 `"use client"`。
- 案件路由固定为动态运行；案件 API 和下载响应使用 `Cache-Control: no-store, private`。

## 4. 路由与四步工作台

```text
/
/matters/[matterId]/facts
/matters/[matterId]/application
/matters/[matterId]/review
/matters/[matterId]/export
```

路由语义：

- `/`：适用条件、创建事项、最近本地事项和删除事项。
- `facts`：步骤 1“当事人与依据”，统一承载执行依据和身份证材料上传。
- `application`：步骤 2“申请内容”。
- `review`：步骤 3“检查与预览”。
- `export`：步骤 4“导出”。
- Header 的“本机运行”入口打开 `RuntimeStatusDialog`，显示能力摘要和安全重试，不新增设置页面，也不出现账号、模型、远程服务或平台配置。

路由守卫以服务端返回的步骤可达性和稳定错误码为准，前端禁用按钮只是提前反馈，不是安全或业务门禁。用户直接访问未解锁路由时，页面显示缺失条件并提供返回修正的唯一明确入口。

## 5. 页面流程与设计实现

### 5.1 首页：`EligibilityGate`

首页固定展示 1—4 编号条件：

1. 用户是生效法律文书中享有权利、准备本人办理申请执行的当事人，不委托律师或其他代理人。
2. 本次申请只有一名自然人申请执行人和一名自然人被执行人。
3. 执行依据是民事调解书或民事判决书，且只有一项明确金钱给付义务。
4. 用户会人工核对姓名、证件号、金额、履行情况和请求事项。

编号条件不是四个复选框。其下只有一个“我已阅读并确认以上 4 项全部符合”复选框；选中后才启用“新建强制执行事项”。提交时写入适用条件版本，不只保留浏览器布尔值。

最近事项的标题遵守同一 Header 规则：无执行依据或案号未确认时显示“待上传执行依据”，不得预填示例案号或把文件名冒充案号。

### 5.2 步骤 1：当事人与依据

页面顺序固定，按完成状态渐进展开：

1. 上传执行依据。
2. 核对执行依据字段。
3. 上传并确认申请执行人身份证正反面。
4. 核对唯一被执行人；身份证正反面如有则上传，缺失字段可手工补充。

执行依据支持 PDF、DOCX、JPG、PNG。上传状态必须显示待上传、上传中、解析中、已提取待确认、已确认、低质量、失败或失效，不使用无限 loading 隐藏真实阶段。

申请执行人身份证正反面是步骤门禁，但“识别成功”不是门禁：两面文件存在后，即使 OCR 失败，也可以查看原图并手工填写，再由用户确认。被执行人身份证不是硬性必需；被执行人姓名必须确认，其他材料未明确的字段标记为用户填写或待补充。

证件住址只能作为“身份证住址候选”。若用户点击“带入送达地址”，前端发送一次显式字段复制 mutation；目标字段记录 `origin=user`、`copied_from_field_id` 和只用于核对的 `related_source_refs`，`confirmation_status` 变为 `extracted_pending_confirmation`。模板仍只读取目标字段重新确认后的值。不得在上传或识别成功后自动覆盖送达地址。

继续步骤 2 的前端提示条件：

- 执行依据已上传、解析流程结束并完成关键依据字段核对。
- 申请执行人身份证正反面均存在，申请执行人关键信息已人工确认。
- 唯一被执行人姓名已确认。
- 服务端没有范围阻断。

不满足时使用对应具体文案，例如“请先上传并核对执行依据”或“请上传并确认申请执行人身份证信息”，不只显示“操作失败”。

### 5.3 步骤 2：申请内容

页面顶部先展示提取摘要：“已从执行依据提取 1 项主要金钱义务”，同时提供来源文件、页码和“查看原文”。提取内容是候选，不自动写入申请书。

页面只包含：

- 一项主要金钱给付义务。
- 文书金额、已履行金额、用户确认的附加金额和尚未履行金额。
- 确定性公式与公式版本。
- 申请法院、请求事项、收款账户、送达地址和已知财产线索。

来源白名单固定为：主要义务、文书金额、履行期限和请求事项候选来自 active `legal_basis`；已履行金额来自 `performance_evidence` 或用户填写；尚未履行金额来自版本化 `AmountComputation`。身份证件不得成为义务或金额来源。

作出法院只作为申请法院候选。用户点击“带入申请法院”后，同样记录 `origin=user`、`copied_from_field_id` 和 `related_source_refs`，目标字段仍需单独确认；前端不得因为字符串相同而自动确认。金额、请求事项、申请法院和送达地址全部确认后，才能进入检查。

不提供多义务列表、复杂分期、自动利率、迟延履行利息法律参数或可自由添加的角色/请求模块。

### 5.4 步骤 3：检查与预览

先调用版本化校验，再按 `blocking`、`warning`、`info` 三类展示：

- `blocking`：不能生成，每项提供准确返回步骤和字段定位；不提供忽略按钮。
- `warning`：可以继续，但必须显示需要人工核对的原因。
- `info`：说明草稿、未提交法院和地方要求边界。

`unsupported_*` 范围错误使用整页或强提示“当前版本不适用”。OCR 误报可以回步骤 1 修正；确认确属复杂案件时只能停止生成。

校验通过后创建生成任务。右侧 `DocumentPreview` 初始显示“等待生成”；生成成功后从 `Generation.preview_manifest` 读取页数、尺寸、hash 和发布状态，再按当前可见页请求后端渲染的 PNG。缩放和旋转只改变图片展示层，不改变来源坐标或服务端文件。预览同时提供页码、已脱敏文本摘要和下载后使用 Word/WPS 复核的说明，不能只提供图片。

### 5.5 步骤 4：导出

导出页展示数据版本、校验版本、模板版本、生成时间和文件 hash 元数据。只有 `generated_revision === data_revision` 且状态为可预览时才允许最终确认。

用户完成三项确认后调用 `PUT /api/v1/generations/{generationId}/export-attestation`：

- 已人工核对姓名、证件号、案号、法院、金额和请求事项。
- 知道文件仍是草稿，需要自行签字并按法院要求提交。
- 已自行核对目标法院的地方材料要求。

服务端确认成功后才启用下载。任何影响卷宗的数据变化都立即把旧下载标记为失效，并要求重新校验、生成和最终确认。

## 6. Header、步骤导航与状态模型

### 6.1 Header 标题契约

前端不自行拼接事项标题，以 `MatterSummary` 的稳定字段渲染；保存状态来自当前 RTK Query mutation 生命周期，不要求后端在 Matter 中持久化：

```ts
type MatterTitleState =
  | "pending_basis"
  | "processing_basis"
  | "case_number_pending_confirmation"
  | "case_number_ready";

interface MatterHeaderView {
  title_state: MatterTitleState;
  display_title: string;
  data_revision: number;
  // 仅前端视图状态，由 mutation 生命周期和 409 响应派生
  save_state: "saved" | "saving" | "conflict";
}
```

显示规则：

| `title_state` | Header 主标题 | 辅助状态 |
|---|---|---|
| `pending_basis` | 待上传执行依据 | 新事项 · 已保存 |
| `processing_basis` | 正在识别执行依据 | 本机处理中 |
| `case_number_pending_confirmation` | 案号待确认 | 已提取 · 请核对 |
| `case_number_ready` | 服务端 `display_title` 中的已确认案号 | 已确认 · 数据版本 N |

案号候选不得在 `case_number_ready` 前伪装为最终事项标题。替换或删除执行依据后由后端推进 revision 并回退状态，Header 用 220ms 状态动效切换，不保留旧案号造成误导。

### 6.2 通用状态

候选与字段确认状态统一为：

```text
pending
processing
extracted_pending_confirmation
confirmed
invalidated
```

材料处理单独使用后端 `processing_status=pending|processing|succeeded|needs_attention|failed|invalidated`；Job 使用其六种队列状态。它们不得与字段确认状态混用，也不得把上传或解析成功映射为“用户已确认”。页面严重级别统一为 `blocking | warning | info`。步骤状态直接使用服务端 `step_gates` 映射为 `locked | available | current | complete | blocked`。

颜色只强化语义，必须同时有文字和图标。所有业务跳转和按钮禁用都读取结构化状态或错误码，不匹配中文 message。

## 7. 组件分层

### 7.1 `packages/ui` Web 通用组件

- `ActionButton`：primary、secondary、text、danger、disabled、loading。
- `StatusBadge`：neutral、info、success、warning、danger。
- `FieldFrame`：label、help、error、尾部操作和描述关联。
- `ConfirmBand`：通用确认区布局，不内置案件规则。
- `IssueRow`：严重级别、标题、说明和定位操作。
- `ResponsiveDialog`：桌面 Dialog、窄屏全宽 Sheet，统一焦点管理。
- `AppGrid`、`Panel`、`Stack`：稳定布局原语。

### 7.2 `apps/web` 领域组件

- `AppHeader`：事项标题、保存状态、数据版本和本机运行状态。
- `StepNavigation`：四步的锁定、当前、完成和阻断状态。
- `EligibilityGate`：四条条件和一个总确认门禁。
- `LegalBasisUpload`：执行依据上传、解析与替换失效。
- `PartyIdentitySection`：申请执行人/被执行人的双面证件上传和确认差异。
- `SourceField`、`SourceViewer`：候选、来源、置信度、确认与失效；来源页使用后端页图并按 normalized bbox 叠加高亮。

- `DownloadRow`、`VersionStrip`：下载门禁与版本一致性。
- `RuntimeStatusDialog`：展示 API/worker/预览能力摘要和可恢复操作，不承担系统配置。
- `UnsupportedCasePanel`：不可绕过的产品范围终止状态。

领域组件只组合生成契约和通用 UI，不复制后端范围规则。组件 props 使用稳定枚举并做穷尽检查，新增状态未处理时 TypeScript 编译失败。

## 8. 设计 token、主题与动效

### 8.1 Token

`packages/design-tokens` 至少定义：

- 语义颜色：canvas、surface、surface-soft、surface-warm、ink、muted、line、brand、accent、success、warning、danger、focus。
- 字号和行高：页面标题、区块标题、正文、辅助文本。
- 间距：4/8/12/16/20/24/32。
- 圆角：8/10/12/16 和圆形。
- 阴影：悬浮操作和浮层，正文卡片不滥用阴影。
- 动效：`motion.fast=140ms`、`motion.base=220ms`、`motion.slow=420ms`、`motion.ease=cubic-bezier(.2,.8,.2,1)`。

生产 CSS 为 `light-dark()`、`color-mix()` 提供静态回退值，再用能力查询增强，避免不支持新 CSS 函数时文字或边框不可见。字体只使用镜像内置或系统中文字体，不请求 CDN 字体。

### 8.2 动效

- 140ms：按钮按压、hover、focus 和状态标签切换。
- 220ms：Header 标题、步骤推进、来源高亮、Dialog/Sheet 进入。
- 420ms：上传完成、内容展开和预览生成结果出现。
- 只对 `transform` 和 `opacity` 做主要动画，避免 height/width 大范围动画导致布局抖动。
- shimmer 或进度动画只在真实异步任务运行时出现；旁边必须有“上传中/解析中”等文本状态。
- 来源高亮不自动滚动到让用户失去上下文的位置；触发后焦点仍保持在来源按钮或转入可预测的 Dialog。

当 `prefers-reduced-motion: reduce` 时，所有非必要动画和 smooth scroll 变为即时切换，任务进度、成功、警告和阻断语义仍完整可见。自动化测试分别覆盖正常动效和 reduced-motion。

## 9. 响应式与浏览器兼容

响应式使用一套 DOM 和业务状态：

| 宽度 | 布局 |
|---|---|
| ≥ 981px | 左侧四步导航 + 中央任务区 + 右侧来源/预览；1280px 为桌面视觉基准 |
| 701—980px | 左侧导航 + 主区；来源和预览转 Dialog/Sheet |
| 360—700px | 单列；四步导航压缩为横向步骤条，表单双列改为单列，底部操作保持可见但不遮挡内容 |

实现要求：

- 使用 `minmax(0, 1fr)`、`min-width: 0` 和安全换行，长案号、法院名、文件名不能撑破布局。
- 移动 Web 触控目标不小于 44×44 CSS px；桌面紧凑按钮可使用 38px 视觉高度，但交互热区不能低于可访问要求。
- 不依赖 `100vh` 固定高度；使用 `dvh` 能力增强并兼容移动浏览器地址栏和安全区。
- 表单、上传、来源查看、阻断、预览和导出均须在 360px 完成，不将“缩小桌面页面”视为移动兼容。
- 目标浏览器政策为当前维护范围内最近两个主要版本的 Chrome、Edge、Firefox、Safari，以及相应 Android/iOS WebView；具体版本由发布时的 Browserslist 锁定并在 CI 输出。
- 本地字体、图标和页面预览资源都通过同源受控地址提供，不依赖运行时外网。

未来微信小程序只复用 `packages/contracts`、`packages/design-tokens` 和经过纯函数测试的领域映射；网络层、上传控件、路由、Dialog、分页图片预览和 DOM UI 由小程序端重新实现。

## 10. 可访问性与敏感信息交互

目标为核心流程达到 WCAG 2.2 AA：

- 所有 input 有可见 label，帮助、错误与状态通过 `aria-describedby` 关联。
- 键盘可以完成新建、上传触发、表单核对、来源查看、校验、最终确认和下载。
- `:focus-visible` 使用高对比 focus ring；不能只通过颜色表达成功、警告或阻断。
- 异步普通状态使用 `aria-live="polite"`；导致流程停止的错误使用聚合后的 `role="alert"`，避免每个字段同时打断读屏。
- Dialog/Sheet 打开后聚焦标题或第一个可操作项，关闭后归还触发按钮；Esc、遮罩和关闭按钮行为一致。
- 步骤导航使用 `aria-current="step"`，禁用步骤同时提供不可达原因。
- 身份证号、账户、电话和详细地址默认脱敏；“查看明文”使用 `aria-pressed` 表达状态，并在切换事项、关闭来源面板或页面失焦后重新脱敏。
- 预览页图不是唯一信息渠道；页码、文本摘要、问题列表、字段来源和导出文件名都有文本等价信息。
- 自动化使用 axe 做基础扫描，但键盘顺序、读屏提示和敏感信息揭示仍保留人工验收。

## 11. Redux、表单与 RTK Query

### 11.1 Store

```ts
export const makeStore = () =>
  configureStore({
    reducer: {
      [api.reducerPath]: api.reducer,
      workspaceUi: workspaceUiReducer,
      sourceViewer: sourceViewerReducer,
    },
    middleware: (getDefaultMiddleware) =>
      getDefaultMiddleware({ serializableCheck: true }).concat(api.middleware),
    // 案件数据由 RTK Query 保存在 store；P0 默认所有模式关闭 DevTools
    devTools: false,
  });
```

当前步骤由 pathname 与服务端 `step_gates` 派生，不写 Redux。`workspaceUiSlice` 只存用户主动调整的导航折叠、辅助面板开合和分栏宽度；dirty 表单及离开提示留在当前 React Hook Form/导航守卫中。事项 ID 以路由为准。`sourceViewerSlice` 只存文档 ID、parse revision、页码、缩放和高亮 ID，不存 OCR 文本。运行能力继续由 RTK Query 的 `Runtime:capabilities` 管理，组件直接使用 selector 派生摘要，不再增加普通 slice 双写。

### 11.2 表单

- 每个页面按提交边界拆分 React Hook Form，避免一个巨型表单导致无关字段重渲染。
- Zod 只做输入格式、必填和前端可即时判断的约束；人数、义务数量、来源有效性、金额和生成门禁由后端再次校验。
- 服务端 `422` 使用稳定 field path 映射到表单；无法定位的错误进入页面级错误摘要。
- mutation 发起时记录本次提交的表单快照；成功后以响应 revision reset，失败时保留 dirty 值。
- `409 revision_conflict` 不静默覆盖。先获取最新服务端版本，展示冲突字段，允许用户取消或显式重新应用仍有效的本地修改。

### 11.3 RTK Query cache

建议 tags：

```text
Matter:{matterId}
Documents:{matterId}
Facts:{matterId}
Dossier:{matterId}
Validation:{matterId}:{revision}
Generation:{matterId}:{revision}
Job:{jobId}
Runtime:capabilities
```

mutation 成功后使用服务端返回的 `data_revision` 更新 Matter，并使旧 Dossier/Validation/Generation 精确失效。不得通过全量 `resetApiState` 掩盖 tag 设计问题。

页面离开或任务进入终态后立即停止轮询。前台对短任务默认每 1 秒轮询，页面不可见时降低到每 5 秒；请求使用 abort signal，避免事项切换后旧响应写回新页面。后续可替换 SSE，但 P0 不实现第二套实时协议。

## 12. API 与跨方案契约

统一前缀 `/api/v1`。部署是否本地由 `runtime.capabilities.deployment_mode=local` 表达，不把 `local` 固化到 URL，避免未来 Web/微信小程序形成两套业务契约。

主要接口：

| 用户动作 | API | 前端处理 |
|---|---|---|
| 新建事项 | `POST /api/v1/matters` | 带适用条件版本和 `Idempotency-Key`，跳转步骤 1 |
| 最近事项 | `GET /api/v1/matters/recent` | 只渲染服务端标题状态和进度摘要 |
| 获取事项 | `GET /api/v1/matters/{id}` | 渲染 Header、revision、步骤可达性 |
| 重新确认/撤销适用条件 | `PUT /api/v1/matters/{id}/eligibility` | 带 `expected_revision`；推进版本并使旧校验/生成失效 |
| 删除事项 | `DELETE /api/v1/matters/{id}` | 二次确认后删除；成功即清理该事项前端 cache |
| 上传材料 | `POST /api/v1/matters/{id}/documents` | 传 `document_kind`，刷新 Documents/Matter |
| 修改/删除材料 | `PATCH/DELETE /api/v1/documents/{id}` | 显示受影响字段；成功后按新 revision 失效来源 |
| 重新解析材料 | `POST /api/v1/documents/{id}/parse-jobs` | 带版本和幂等键，刷新 Document/Job |
| 查询任务 | `GET /api/v1/jobs/{jobId}` | 仅活动态轮询 |
| 查看来源页 | `GET /api/v1/documents/{id}/pages/{page}` | 会话内按文档 parse revision 缓存 |
| 获取事实 | `GET /api/v1/matters/{id}/fact-fields` | 渲染候选、来源和确认状态 |
| 确认字段 | `PUT /api/v1/matters/{id}/fact-fields/{fieldId}` | 带 `expected_revision`，失效旧校验/生成 |
| 获取确认卷宗 | `GET /api/v1/matters/{id}/dossier` | 读取固定角色视图和 `AmountComputation` |
| 保存申请 | `PUT /api/v1/matters/{id}/application` | 同上，不隐式映射字段 |
| 运行校验 | `POST /api/v1/matters/{id}/validations` | 返回 blocking/warning/info |
| 生成文书 | `POST /api/v1/matters/{id}/generations` | 带幂等键，创建 Generation/Job |
| 获取生成记录 | `GET /api/v1/generations/{id}` | 读取状态、版本和 `preview_manifest` |
| 获取预览页 | `GET /api/v1/generations/{id}/preview/pages/{page}` | 按可见页获取受控 PNG，不接受文件路径 |
| 最终确认 | `PUT /api/v1/generations/{id}/export-attestation` | 三项确认后由服务端开放下载 |
| 下载文件 | `GET /api/v1/generations/{id}/files/{fileId}` | 仅当前版本且已声明；使用同源受控地址和服务端文件名 |
| 查看能力 | `GET /api/v1/runtime/capabilities` | 启动和诊断页获取 |

P0 `document_kind` 固定为：

```text
legal_basis
applicant_id_front
applicant_id_back
respondent_id_front
respondent_id_back
performance_evidence
```

字段来源统一为以下语义；实际代码只导入 OpenAPI 生成类型，不手写维护另一套 enum：

```ts
interface ConfirmableField<T> {
  value: T | null;
  origin: "source" | "user";
  source_refs: Array<{
    document_id: string;
    parse_revision: number;
    source_span_id: string;
    page_number: number;
    bbox_normalized?: [number, number, number, number] | null;
  }>;
  copied_from_field_id?: string | null;
  related_source_refs?: Array<{
    document_id: string;
    parse_revision: number;
    source_span_id: string;
    page_number: number;
    bbox_normalized?: [number, number, number, number] | null;
  }>;
  extraction_method:
    | "embedded_text"
    | "ocr"
    | "regex"
    | "dictionary"
    | "layout"
    | "user_input";
  confidence: number | null;
  confirmation_status:
    | "pending"
    | "processing"
    | "extracted_pending_confirmation"
    | "confirmed"
    | "invalidated";
}
```

用户填写字段 `confidence=null`。来源查看以 `source_refs` 为准，客户端不得用 OCR 字符串搜索自行猜测页码或坐标。尚未履行金额等确定性结果不伪装成 `ConfirmableField` 或材料候选；前端使用 OpenAPI 生成的 `AmountComputation`，展示 `input_field_revisions`、`formula_version`、`currency`、十进制字符串 `result` 和确认状态。输入版本变化即显示 `invalidated`，重新确认后才进入快照。

任务状态：

```text
queued
running
retry_scheduled
succeeded
failed_terminal
cancelled
```

同时显示 API 的 `retryable`、`attempt`、`max_attempts` 和可选 `progress`。`progress` 只按 0—100 粗粒度阶段展示，并明确不代表线性剩余时间；字段缺失时只显示真实状态，不根据轮询次数伪造百分比。`retry_scheduled` 不显示成终态失败，`failed_terminal` 提供稳定错误码、手工回退或重试入口。

创建事项尚无既存 revision，只提交适用条件版本和 `Idempotency-Key`；其余会修改事项、字段、材料、校验、生成、重试或最终确认的请求携带 `expected_revision` 和 `Idempotency-Key`。前端依据稳定 error code 处理 `409`、`413`、`415`、`422`、`429` 和 `503`，错误信息不得展示服务端绝对路径、OCR 正文或敏感值。

## 13. 错误恢复、阻断与版本一致性

| 场景 | 前端行为 |
|---|---|
| 上传中断 | 保留已选文件名的脱敏显示，允许重试或移除，不创建重复文档 |
| OCR/规则失败 | 显示原文/原图和手工填写；简单案件可继续 |
| 多当事人/代理人/多义务 | 显示“当前版本不适用”，生成操作消失或禁用，不提供忽略 |
| 来源删除/替换 | 受影响字段进入 `invalidated`，Header、校验和生成版本同步失效 |
| revision 冲突 | 保留未提交输入，获取最新数据并显式处理冲突 |
| API 暂时不可用 | 显示本机服务连接状态和重试，不把事项标记为失败 |
| worker 终态失败 | 展示稳定错误说明；允许服务端声明的安全重试或手工回退 |
| 预览失败 | 不开放下载；保留生成记录并引导重新生成/查看诊断 |
| 数据修改后旧文书过期 | `VersionStrip` 显示失效，下载禁用，重新校验和生成 |

阻断码至少覆盖：

```text
eligibility_not_confirmed
unsupported_multiple_applicants
unsupported_multiple_respondents
unsupported_representative
unsupported_organization_party
unsupported_basis_type
unsupported_multiple_obligations
unsupported_complex_obligation
```

UI 不通过 warning 样式弱化这些错误。中文 message 可优化表达，但行为只由 code 和结构化 details 决定。

协议错误码必须有确定 UI 行为：

| error code | 前端处理 |
|---|---|
| `revision_conflict` | 保留 dirty 输入，读取最新 revision 并进入显式冲突处理 |
| `idempotency_key_reused` | 停止自动重试，生成新 key 前先记录无敏感信息的实现错误 |
| `applicant_identity_sides_required` | 聚焦步骤 1 申请执行人身份证上传区 |
| `basis_case_number_unconfirmed` | 聚焦执行依据案号字段并展示待确认状态 |
| `source_reference_invalidated` | 标记受影响字段失效，刷新 Matter/Fact/Dossier |
| `validation_superseded`、`generation_superseded` | 显示版本失效，禁用预览/下载并引导重新检查 |
| `generation_blocked` | 根据响应中的 issue IDs 展示 blocking 列表，不创建客户端假任务 |
| `export_attestation_required` | 保持下载禁用，聚焦最终三项确认 |
| `job_not_retryable`、`blob_commit_incomplete` | 隐藏普通重试或按服务端能力提供安全恢复，不臆测文件可用 |
| `runtime_capability_unavailable` | 保持事项可查看，仅禁用依赖该能力的上传解析或生成操作 |

范围校验的 blocking issues 可以来自成功的校验响应；客户端不把所有业务阻断都当网络异常。`409` 用于并发、版本、幂等和生成失效，`422` 用于客户端不可能的数据形状。

## 14. 性能与包体控制

### 14.1 运行时性能

- 首页和 Header 不加载预览、来源定位或导出组件；进入对应步骤时再加载页面级 chunk。
- Ant Design 按模块使用，`packages/ui` 禁止 `export * from "antd"`；lucide 按图标导入；不打包无关 locale 和演示数据。
- 上传直接使用 `File`/`Blob` 和 `multipart/form-data`，不转 Base64、不写 Redux；同一事项默认串行上传大文件，替换或取消时中止旧请求，避免移动设备瞬时占用多份文件内存。
- 大文本只在打开对应页时请求，列表接口返回摘要；OCR 全文不进入 RTK Query 长期缓存。
- 来源页 endpoint 设置短 `keepUnusedDataFor`，关闭 viewer 或切换 parse revision 后立即释放旧页缓存；不预取整份扫描文书。
- 输入和来源高亮避免全页面 selector；通过 memoized selector 和页面级表单拆分控制重渲染。
- 来源页图和生成预览使用同源受控 URL，只保留当前页及相邻页并设置固定宽高占位，避免把整份文档转成 Blob 或同时解码到内存。
- 动效只使用合成友好的属性；低性能设备和 reduced-motion 不运行 shimmer、弹性或连续位移动效。

### 14.2 可执行预算

在 production build 的虚构样本环境检查：

- 首页 First Load JS 目标不高于 250 KB gzip。
- 每个业务路由的项目自有增量 JS 目标不高于 80 KB gzip；来源定位和预览作为页面级按需 chunk，不计入首页。
- 桌面 Lighthouse Accessibility 目标不低于 95，Performance 目标不低于 85；移动结果记录趋势，不允许因单次无依据优化牺牲可访问性或正确性。
- CI 输出 route bundle 分析；超过预算必须说明新增依赖、替代方案和回归验证，不能静默放宽阈值。

预算是工程门禁目标，不是法律流程正确性的替代指标。

## 15. 构建、容器与产物隔离

Next.js 使用：

```ts
const nextConfig = {
  output: "standalone",
  productionBrowserSourceMaps: false,
};
```

Docker 使用多阶段构建：

1. `deps`：只安装 lockfile 对应依赖。
2. `builder`：运行 contracts codegen、类型检查、测试和 `next build`。
3. `runner`：只复制 `.next/standalone`、`.next/static`、允许的 `public` 运行资源和许可证。

禁止进入 Web 生产镜像或可发布压缩包：

```text
.git/
.github/
outputs/
work/
docs/
**/*design*.html
**/*.pptx
**/*需求*.md
**/*方案*.md
test-results/
playwright-report/
coverage/
.next/cache/
node_modules/.cache/
data/
uploads/
generated-documents/
```

约束：

- `.dockerignore` 从仓库根阻止设计稿、文档、本地数据和测试报告进入 build context；最终 runner 再采用 allowlist copy，形成双重保护。
- `public/` 只放运行必需图标、内置字体和无案件信息的静态资源，禁止把 `outputs/design` 复制进去。
- Turborepo 的生产 outputs 只声明 `.next/**`（排除 `.next/cache/**`）和共享包 `dist/**`；文档不是任务产物。
- 数据、上传件、OCR 缓存和生成文件只挂载到运行时 volume，不存在于镜像层或 Web 构建目录。
- CI 增加 `artifact-audit`：列出 runner 镜像文件并对以上禁用路径/扩展名做失败检查，同时验证无 `.env`、真实材料和绝对本机路径。
- 一键启动由根目录 `docker compose up --build` 统一拉起 web、api、worker、migrate、postgres；只将 Web 绑定到 `127.0.0.1:3000`。

## 16. 安全与隐私

- 不接入第三方 analytics、错误上报、CDN、远程字体或在线预览服务。
- 前端日志只记录 request ID、稳定错误码、路由和耗时分类，不记录请求/响应正文、文件名原文或表单值。
- P0 默认在生产和普通开发模式都禁用 Redux DevTools，因为 RTK Query store 含案件响应。只有专用的纯虚构 fixture profile 才可经 action/state sanitizer 临时启用，错误对象仍不得携带正文。
- 上传前检查扩展名、大小和浏览器声明 MIME 只用于快速反馈，服务端仍做最终 magic bytes 校验。
- 下载 adapter 只创建指向同源受控 endpoint 的临时 `<a>`，由服务端 `Content-Disposition` 提供清理后的文件名；不先 `fetch` 为大 Blob，也不接受客户端文件系统路径。
- 切换事项、退出预览和页面失焦时重新脱敏；不将明文复制到 toast、通知、页面标题或剪贴板，除非用户显式操作。
- CSP 至少限制为本机资源；预览图片和下载只允许同源受控 URL，不为方便调试放宽到任意远程域或 `blob:` 全局来源。

## 17. 测试策略与 MVP 验收矩阵

### 17.1 单元与组件测试

- `makeStore` 每实例创建，RSC 不访问 store，API 数据不复制到普通 slice。
- 首页 4 条编号条件 + 单一总确认；未确认时不能新建。
- Header 的 `pending_basis → processing_basis → case_number_pending_confirmation → case_number_ready`，删除/替换来源后正确回退。
- 申请执行人身份证正反面均存在且信息确认后才解锁步骤 2；OCR 失败允许手填。
- 被执行人身份证可选，姓名确认必需。
- 证件住址不自动写入送达地址，作出法院不自动写入申请法院；显式带入后目标字段重新待确认。
- 候选采纳、修改后采纳、驳回、用户填写、来源跳转和来源失效。
- RTK Query tag 精确失效、页面隐藏轮询降频、终态和卸载停止轮询。
- `409` 冲突保留 dirty 表单，Job 可重试与终态错误区分。
- blocking/warning/info、版本过期、最终确认和下载禁用。
- 默认脱敏、明文按钮、Dialog 焦点归还和 reduced-motion。

### 17.2 契约测试

- CI 从 FastAPI 导出 OpenAPI 并重新生成 RTK Query，`git diff --exit-code` 必须无差异。
- 对 `MatterTitleState`、`confirmation_status`、`document_kind`、Job 状态和 blocker code 做穷尽编译检查。
- MSW fixture 必须通过生成 schema，不维护手写的另一套响应类型。
- 除创建事项外，每个修改型 mutation 验证 `expected_revision`；创建、上传、解析重试、生成和最终确认验证 `Idempotency-Key`。

### 17.3 Playwright 与视觉回归

- 文本型民事调解书的四步主流程。
- 扫描型民事判决书 OCR 后修正、手工填写并导出。
- 部分履行的确定性金额计算和来源查看。
- 多被执行人、代理关系和多项独立义务稳定阻断。
- OCR 失败但简单案件通过原文和手填继续。
- 替换执行依据后 Header 回退、来源失效、旧预览和下载不可用。
- API、worker 重启、`retry_scheduled`、`failed_terminal` 和刷新恢复。
- 360、390、430、768、980、1280、1440px 无横向溢出、遮挡、焦点丢失和不可达操作。
- 键盘全流程、axe 基础扫描、正常动效和 `prefers-reduced-motion: reduce`。
- Ant Design 首屏无样式闪烁和 hydration error。

所有材料、姓名、案号、证件号、地址、账户和金额使用明显虚构样本。视觉快照只保留脱敏界面，不包含上传件、OCR 全文或生成文书正文。

### 17.4 发布验收

- 类型检查、lint、单元、组件、契约、Playwright 和 artifact audit 全部通过。
- 支持样本均可在人工修正后完成草稿导出；不支持样本生成数量为 0。
- 未确认字段进入生成上下文数量为 0；旧 revision 可下载数量为 0。
- DOCX/PDF/PNG 预览完成服务端视觉检查；前端在桌面和移动 Web 均能查看状态并下载当前版本。
- 生产镜像中设计稿、需求/方案文档、Git 元数据、测试材料、本地数据和构建缓存数量为 0。

## 18. 实施顺序

### 里程碑 1：工程基线与手工闭环

- pnpm workspace、Turborepo、Next.js App Router、standalone 和产物审计。
- Redux Toolkit、RTK Query、OpenAPI codegen、tokens 和 Web UI 基础。
- 首页适用门禁、Header 状态、四步布局和固定表单。
- 不依赖 OCR 的手工录入、校验、生成、预览和导出闭环。

### 里程碑 2：材料、身份证与来源

- 执行依据、申请执行人双面身份证、被执行人可选身份证和履行材料上传。
- Job 状态、后端页图、来源高亮、候选确认和手工回退。
- 来源替换、字段失效和 Header 回退。

### 里程碑 3：可靠检查与响应式体验

- 范围阻断、问题定位、数据版本失效和最终确认。
- 桌面三栏、窄屏 Dialog/Sheet、移动单列和键盘/读屏体验。
- 动效、reduced-motion、性能预算和错误恢复。

### 里程碑 4：发布门禁

- 支持/不支持虚构样本、契约漂移、端到端和视觉回归。
- production bundle 分析、多阶段镜像和 artifact audit。
- 一键启动、重启恢复、备份/删除和隐私说明联调。

每个里程碑都必须保持可运行闭环，不以大量空路由、空包或第二版 feature flag 作为“扩展性”成果。

## 19. 第二版和微信小程序扩展点，只规划不实现

第二版可按业务验证结果增加身份入口、律师工作台、多角色、组织主体和可选 AI 候选抽取，但 MVP 不创建相关页面、slice、API client 或隐藏开关。

微信小程序演进边界：

```text
可复用：packages/contracts
        packages/design-tokens
        packages/doc-fields 中无 DOM 的元数据
        金额展示、状态映射等纯函数及测试向量

不可直接复用：Next.js 路由
            React DOM / Ant Design 组件
            Redux Provider 实例
            RTK Query Web 下载实现
            分页图片预览、Dialog、文件 input 和浏览器 API
```

小程序启动时新增独立 adapter 和 UI，实现相同的 revision、来源、确认、阻断和导出语义。不得为了“代码复用”让 MVP Web 依赖小程序运行时或引入跨端框架。

## 20. 风险、替代方案与验证

| 风险/决策 | 当前方案 | 替代方案 | 验证方式 |
|---|---|---|---|
| Next.js + Redux 跨请求污染 | 客户端 `makeStore` 按实例创建，RSC 不读 store | 取消 Redux，仅用 Context | 并发渲染测试、刷新和多事项切换 |
| Ant Design 包体和视觉约束 | 只使用必要控件、Web wrapper、模块导入、预算门禁 | 全部自研或 headless UI | bundle analyzer、设计视觉回归、可访问性测试 |
| React Hook Form 与 AntD 双状态 | RHF 是唯一表单状态，AntD 只提供控件 | 只用 AntD Form | dirty/错误/409 恢复测试 |
| 大页图造成移动端内存上涨 | 只保留当前页及相邻页，固定占位并让离屏图片卸载 | 原生 PDF iframe | 长文档滚动、内存和移动端预览测试 |
| Header 用未确认案号误导 | 服务端 title state；仅确认案号进入 ready | 客户端用文件名或候选案号 | 状态机和替换来源回归 |
| 响应式分叉形成两套产品 | 同一 DOM、契约和状态，CSS 布局切换 | 单独移动 Web 应用 | 多 viewport E2E 和无障碍测试 |
| 跨端复用导致 DOM 泄漏 | contracts/tokens/纯函数可复用，UI 分端实现 | 引入跨端框架 | dependency-cruiser 边界检查 |
| 构建产物携带设计/需求文档 | `.dockerignore` + runner allowlist + artifact audit | 构建后手工删除 | CI 列表和 denylist 失败测试 |
| 为未来功能过度开发 | 只保留契约和包边界，不建空功能 | 预先创建律师/AI/小程序目录 | 仓库结构审查和 MVP 路由断言 |
